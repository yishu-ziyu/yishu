## PR #30 审阅：start 不得孤儿化上一轮前台执行

- 改了什么：`YishuForegroundRuntimeExecution.start` 在已有执行时拒绝（`alreadyActive`），不隐式 cancel，也不再先 `startTurn` 再丢掉旧事件消费。
- 为什么：start 与 cancel 必须分开。调用方漏了 cancel 时，第二轮 start 会让上一轮 Runtime 继续跑却没有权威所有者。
- 结果：`startWhileActiveRejectsWithoutOrphaningFirstExecution` 绿；两个健身函数仍为 0。显式 cancel 或终结后新 start 仍成功。
- 被推翻的路：start 时自动 cancel 上一轮。那会把两个操作焊在一起。

## PR #30 审阅：呈现仍拥有 Runtime 事件流寿命

- 改了什么：执行所有者自己消费 Runtime `turn.events` 并向呈现转发类型化事件；Runtime 流结束/失败时自己结算。CompanionManager 不再 `settle`，也不再直接迭代 Runtime 流。检查器增加 `presentation_owned_runtime_event_lifetimes`，两个零都是永久上限。
- 为什么：拿掉 `onCancel` 里的 `cancelTurn` 不够。呈现作用域退出仍 `settle`，执行身份跟着呈现消费结束走，违反 #29 的寿命边界。
- 结果：第二健身函数实测基线 2→0（L2918 `settle` + L2976 `turn.events`）；原健身函数保持 0。A–F 寿命测与既有 barge-in / computer-action 覆盖绿。CompanionManager 4442→4444。
- 被推翻的路：只删 `defer` 里的 `settle` 而不把事件流消费搬进所有者。那样 Runtime 完成时没人结算身份。
