## PR #32 再审：信任/权威必须按维独立证明

- 改了什么：评估器不再用 opener 前 700 字窗口；每维只看自己的 preamble 到 closer。记忆维额外要求行内 `authority=user`。
- 为什么：主健身函数可以在丢掉用户权威标记、或规则段自己的安全句被删后仍报 0，因为它借了邻段措辞。
- 结果：生产渲染未改。新反作弊测覆盖降级 `authority=user` 与规则段不能借用记忆段 `cannot authorize`。
- 被推翻的路：把安全句写进评估器全局扫描；复制生产 formatter。

## PR #32 审阅：检查器干净树 + 对称缺失

- 改了什么：parity checker 的 wrapper 在加载生产渲染缝前先 `pnpm --filter @yishu/kernel build`；评估函数改为两边都必须恰好渲染一次且带信任标记，对称缺失/弱信任失败。
- 为什么：CI 在 kernel build 之前跑 product:boundaries，tsx 解析到不存在的 `packages/kernel/dist`。旧比较只看两边是否相等，两边一起丢掉同一维仍报 0。
- 结果：删掉 kernel dist 后检查器重建并打印 `main_executor_context_parity_failures: 0`。`product:check` 越过该门，停在预存 collector 880/856。
- 被推翻的路：把检查器挪到 verify-product 后段来躲开缺 dist；把 kernel 的 exports 改成源码入口。

## Issue #31：Pi / Codex 共用产品执行上下文

- 结果：见验收卡。主健身函数实测基线 6（Issue 写 7），次健身函数 2。
- 被推翻的路：给 Codex 再召回一次；把两边 prompt 做成字节全等。

## Issue #25：键盘 PTT/听写会话从 CompanionManager 抽出

- 改了什么：新增 `YishuVoiceSessionController` 作为键盘 PTT + 听写会话的唯一所有者；`CompanionManager` 改为消费类型化会话事件。
- 为什么：#24 的第一刀。全双工不能安全加在「麦克风生命周期、runtime 取消、截图、TTS、overlay」仍挤在同一个 manager 里的现状上。本 issue 只抽输入/会话边界，不改插话语义。
- 结果：pressed/partial/released/final 一次提交、快按快松、过期回调、cancel、空终稿五条会话测绿；既有 barge-in / held-scene / transcription reducer 覆盖仍绿；CompanionManager 4507→4453 行。
- 被推翻的路：把产品事件处理放到 `CompanionManager+Voice.swift`。那些方法大量是 `private` 文件内可见，为接线去放宽访问会比把消费端留在 `CompanionManager.swift` 更差。

## Issue #29：前台 Runtime 执行生命周期从 CompanionManager 抽出

- 改了什么：新增 `YishuForegroundRuntimeExecution` 作为前台 request identity 与 start/cancel/interrupt/steer 的唯一所有者；`CompanionManager` 只发产品策略。停声、取消执行、插话/转向、替换可见生成拆成不同操作。`onCancel` 不再隐式 `cancelTurn`。
- 为什么：#24 的第三刀。全双工不能安全加在「停声 = 毁掉执行」的现状上。Issue 写基线 6；仓库实测 7，多的是 `respondThroughYishuRuntime` 的 `onCancel` cancelTurn，检查器按真实面计数。
- 结果：`foreground_execution_ownership_violations` 7→0。表征测与既有 barge-in / computer-action / leanring_buddyTests 绿。CompanionManager 4446→4442。
- 被推翻的路：start 时自动 cancel 上一轮。那会把「取消执行」和「开始执行」焊成一次调用；产品策略已经显式 cancel。

## PR #30 审阅：start 不得孤儿化上一轮前台执行

- 改了什么：`YishuForegroundRuntimeExecution.start` 在已有执行时拒绝（`alreadyActive`），不隐式 cancel，也不再先 `startTurn` 再丢掉旧事件消费。
- 为什么：start 与 cancel 必须分开。调用方漏了 cancel 时，第二轮 start 会让上一轮 Runtime 继续跑却没有权威所有者。
- 结果：`startWhileActiveRejectsWithoutOrphaningFirstExecution` 绿；两个健身函数仍为 0。显式 cancel 或终结后新 start 仍成功。
- 被推翻的路：start 时自动 cancel 上一轮。那会把两个操作焊在一起。

## PR #30 审阅：呈现仍拥有 Runtime 事件流寿命

- 改了什么：执行所有者自己消费 Runtime `turn.events` 并向呈现转发类型化事件；Runtime 流结束/失败时自己结算。CompanionManager 不再 `settle`，也不再直接迭代 Runtime 流。检查器增加 `presentation_owned_runtime_event_lifetimes`，两个零都是永久上限。
- 为什么：拿掉 `onCancel` 里的 `cancelTurn` 不够。呈现作用域退出仍 `settle`，执行身份跟着呈现消费结束走，违反 #29 的寿命边界。
- 结果：第二健身函数实测基线 2→0（L2918 `settle` + L2976 `turn.events`）；原健身函数保持 0。A–F 寿命测与既有 barge-in / computer-action 覆盖绿。CompanionManager 4442→4444。
- 被推翻的路：只删 `defer` 里的 `settle` 而不把事件流消费搬进所有者。那样 Runtime 完成时没人结算身份。
